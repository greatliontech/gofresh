# Repository Directives & Compaction Defense

## Compaction Defense & Per-Chunk Working Notes (`docs/notes/`)

Context compaction is the primary operational hazard on multi-chunk work. Treat ephemeral conversation memory as volatile and `docs/notes/<chunk-slug>.md` in Git as the active chunk's working memory — never as a cumulative multi-chunk append-only log:

1. **Per-Chunk Lifecycle (Provide to Reviewer, Delete at Close-Out):** Create one dedicated working-notes file (`docs/notes/<chunk-slug>.md`) per active chunk, promote contracts to `docs/specs/`, mechanism rationale to package/module doc comments (and local constraints to code comments), and tracked deferrals (with concrete `Lands:` slots) to `docs/issues/<slug>.md` **before** final review convergence so those artifacts are reviewed alongside `docs/notes/<chunk-slug>.md`, and **delete `docs/notes/<chunk-slug>.md` at chunk close-out** (staging its deletion in the chunk close-out commit once review converges to `ZERO FINDINGS` and recording process reasoning in the commit message). `docs/notes/` stays empty between chunks; cross-chunk discoveries belong in tracked `docs/issues/<slug>.md` files or `docs/plans/plan.md`.
2. **Read First After Startup or Compaction:** Always read `docs/plans/plan.md` (when present), any active `docs/notes/<chunk-slug>.md`, and open `docs/issues/` scheduled for the chunk (when present) before designing or editing code so active chunk boundaries, prior audit findings, rejected dead ends, and user decisions are loaded intact.
3. **Continuous In-Chunk Updates & Standalone Commits:** Record every architectural alignment with the user, root-cause diagnosis, soundness or performance audit result, hypothesis, and review disposition in the active `docs/notes/<chunk-slug>.md` as it happens — never defer note-taking until chunk close-out. Commit standalone `docs(notes): ...` / `docs(plan): ...` updates (staging only the intended doc files without sweeping in uncommitted code) whenever a pre-implementation audit, user alignment, or milestone completes.
4. **Never Pile Cross-Chunk Edits onto an Uncommitted Tree:** Keep each active chunk isolated, adversarially reviewed, verified, and committed (with its working-notes file deleted) before starting the next chunk.

## Scope, Authority & First-Principles Architecture

1. **5-Repo Ownership (Including Autonomous Commit & Push):** Full ownership of specs, code, commits, and pushes (`git push`) spans `go-x-tools`, `gofresh`, `gomutant`, `stipulator`, and `pew` — push converged, verified work directly without asking for confirmation. Keep `godst` outside repository modification scope unless explicitly requested.
2. **Toolchain Flavor Invariance:** Every analysis, guard, build, and test across the 5 repos must work identically under both `godst` (custom Go builds) and vanilla / system-installed Go toolchains, with zero flavor-specific or Go-version-list hardcoding.
3. **Zero Third-Party Module/Version Allowlists:** `gofresh` analyzes arbitrary user subject repositories and their transitive dependencies, not just our own tools. Never add third-party module or semver allowlists (`VersionListing`) to `internal/auditset` or `internal/closure` to paper over an analysis gap:
   - Valid Go constructs (such as startup dead-branch pruning on unmutated zero globals, memoizer patterns, interface/parameter closure, and sentinel globals) must be analyzed mechanically from first principles.
   - Non-toolchain `.s` assembly must be verified mechanically on disk per `TEXT` symbol (checking `RODATA` globals, `(SB)` symbol discipline, absence of syscalls/traps/clocks/RNGs, decoded ISA feature-query instructions, and carrier-free Go signatures) without naming specific third-party module paths or versions.
   - Only genuine non-derivable external blindspots require explicit caller authority (`//gofresh:pure` or dependency-boundary vouches).
4. **Stipulator Static-Records-Only Flow Before Release & Upgrade:** Because the installed `stipulator` binary links a released version of `gofresh`, never run witness-executing `stipulator` invocations (`stipulator check`, `stipulator gate`, bare `stipulator verify` without `--no-test`, `stipulator prune` without `--no-test` or `--dangling`, or `stipulator gap --list`) while developing unreleased `gofresh` or `stipulator` witness-execution fixes — doing so runs the pre-fix freshness/execution engine across the suite. Prior to cutting an updated `gofresh` release tag and rebuilding/installing `stipulator` against it (or rebuilding/installing `stipulator` for `stipulator`-only fixes), use only static record/authoring commands (e.g., `stipulator compile`, `stipulator pin`, `stipulator bind`, `stipulator unbind`, `stipulator retarget`, `stipulator dispose`, `stipulator attest`, write-mode `stipulator gap`, `stipulator prune --no-test`/`--dangling`, and `stipulator verify --no-test --view bindings`), verifying that every bound `REQ-` row reports `current` and `resolved` (`0` stale, rehash-pending, unpinned, moved, or unresolved rows, since `verify --no-test` exits non-zero only on structural `Problems`), while executing affected witness `Test*` functions directly via `go test` on the working tree. Run full witness-executing `stipulator check` only after the updated `gofresh` release is tagged and linked into a rebuilt/installed `stipulator` binary (or after rebuilding/installing `stipulator` for `stipulator`-only changes).

## Exhaustive Testing, Oracles & Harness Discipline

Treat tests and test harnesses as first-class architectural artifacts designed alongside every mechanism — never as post-implementation or review-driven afterthoughts:

1. **Exhaustive Case-Space Design (Cases, Not LOC):** Before or alongside implementing any executable change, enumerate the orthogonal dimensions and boundary conditions of its input space (type/AST/SSA/CFG combinators, execution modes, cache/memo warm-vs-cold states, cross-mode replay, malformed/adversarial inputs, and negative/positive controls) and cover them via compact, parameterized table-driven matrices that maximize distinct semantic cases rather than line count.
2. **Compositional `pgregory.net/rapid` Properties & Independent Oracles:** Accompany static analyses, type/layout predicates, and semantic verifiers with compositional `rapid` generators checked against independent semantic or executable reference oracles (e.g., byte-level memory/header layout maps via `go/types.Sizes`, runtime state-drift execution oracles, and metamorphic AST/CFG/SSA transformations such as dead-branch insertion, local rebinding, and helper extraction).
3. **`testing.F` Fuzzing on Parsers, Scanners, Lowerings & Codecs:** Pair syntax/assembly/testlog parsers, CFG/IR lowerings, and wire/manifest codecs with `testing.F` fuzz targets seeded from the boundary table cases, asserting crash-freedom, determinism, and round-trip/oracle invariants.
4. **Invest in Reusable Test Harnesses:** Build or extend clean shared in-memory/hermetic test harnesses (`internal/testenv` or focused subsystem harnesses) whenever existing test setup makes exhaustive case generation verbose or duplicative, and verify every new or changed testable invariant kills targeted `gomutant ephemeral` probes (`0` non-equivalent survivors — strengthen tests or demonstrate semantic equivalence) and cannot pass for the wrong reason.
